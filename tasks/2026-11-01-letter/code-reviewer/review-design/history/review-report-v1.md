## Что проверено и принято
- **Покрытие требований.** С-1 → `All`, `Count`; С-2 → `Cycle`; С-3/С-4 → `DistanceUp`/`DistanceDown`; С-5 → `Shift(int)`; С-6 → `Equal` и `==`; С-7 → doc.go, doc-комментарии, примеры, README; Е-1 → таблица «Поведение при недопустимом значении», `FromOrdinal`/`ErrInvalid`/`MustFromOrdinal`; Г-1 → К-8 без переполнения; Г-2 → К-3/К-4; Г-3 → новый срез на вызов. У каждого К-1…К-16 есть способ проверки: тест (plan-1…plan-3), review-design (К-11 а, в, г) или QA (К-11 б, д; К-12, К-15, К-16).
- **Будущие потребители (readiness v1).** system: `DistanceUp` как h_b(l), `Shift` как l′, нетипизированная `Count` для `Count*w + h`; interval: расстояния в обе стороны, `Shift`; notation: `All`, `Ordinal`, `[letter.Count]T`, ключи `map`; spelling: сравнимый однобайтовый тип с недопустимым нулевым значением («не задано»), `Equal`; search/modal: перебор `All`, ключи `map`, линия квинт через `Shift(4)`. Новой функциональности сверх объёма нет.
- **Контракт API (artifacts/architecture, стек Go «Контракт публичного API Go»).** Определены: создание (константы, `FromOrdinal`), нулевое значение и `nil`-указатель, числовые значения вне контракта, равенство `==` и `Equal`, копирование, неизменяемость, владение срезами, ошибки (`errors.Is`, текст не в контракте), паника только в Must, конкурентность, сериализация, обычные и ошибочные примеры.
- **Расхождение `==` и `Equal` на недопустимых значениях — обосновано.** На допустимых буквах они совпадают; `Equal` ложен для любого недопустимого операнда, в том числе `z.Equal(z)`. Иначе `Equal` отвечал бы «это та же буква» для значения, которое буквой не является (П-11, К-7). `==` — оператор языка, пакет им не управляет; архитектура прямо направляет к `Equal`/`IsValid`. Цена — нерефлексивность `Equal` вне семи букв (как у NaN) — названа в Р-5 и проверяется тестами К-7.
- **Крайние значения `int` в `Shift`.** Требование «привести по модулю до сложения» исключает переполнение; ожидаемые значения для обеих разрядностей и исключение `-math.MinInt` в свойстве обратимости указаны верно; тесты считают ожидаемое по `strconv.IntSize`.
- **НФ-1 / К-11 (Q-8 (а)).** а) таблица результатов для N букв по Д-3 модели, при N = 7 совпадает с К-1…К-6; б) формулировки «seven-letter set» заданы для doc.go и doc-комментариев; в) перечень «добавить» конкретен, «изменить» — пусто; г) новые наборы — новые типы, существующий API не меняется, возможные добавления методов к `Letter` совместимы (Р-4 оценён); д) конструктора набора и параметра числа букв нет. Разные Go-типы делают смешение наборов ошибкой компиляции.
- **docs/rules.** Must — `MustFromOrdinal` как обёртка над `FromOrdinal` с паникой ошибкой; самостоятельных Must нет. Equal — есть. Pointer receiver — исключение для `letter` записано в architecture (тип, Q-A2, КР-2) с основанием Q-SA1. Vendor запрещён. Go 1.27.3, golangci-lint v2.15.0, `.golangci.yml` без изменений. Testify v1.11.1 добавляет автор тестов. `t.Parallel()`, табличные тесты с именованными случаями. Ветка `feat/1-add-letter-package` соответствует формату `тип/номер-описание`.
- **План.** Исполнители (go-test-developer / go-code-developer), разрешённые пути и запреты чтения разделены корректно. Полный набор тестов plan-1…plan-3 принимается на review-tests до plan-4. Подход к проверке достаточен: внешний пакет `letter_test`, независимый оракул-литерал с математическим остатком, полный перебор 7 / 49 / 7×31 / 256 значений, гонки под `-race` с `wg.Go` и проверкой в горутине теста, импорты через `go/build` и `go list`, ожидаемые падения до реализации по исключению стека Go. Правильно отмечено, что `assert.PanicsWithError` сравнивает текст и не подходит.
- **Разделение авторов.** Автору тестов не передаются исходники реализации: ограничение «приводить `steps` по модулю до сложения» — требование к результату, а не код. Автор реализации получает имена примеров из architecture и тесты не читает.

## Блокирующие замечания

### Б-1. Команда форматирования в plan-4 пишет в тестовую область; шаги тестов не проверяют порядок импортов gci
- **Место:** implementation-plan v2: «plan-4 — реализация», «Проверка», п. 1 («`golangci-lint fmt ./...` не меняет файлы») и п. 5; «Подход к тестам» → «Ожидаемые падения до реализации» и «Проверка шага» в plan-1…plan-3 (только `gofmt -l`).
- **Суть.**
  1. `golangci-lint fmt ./...` переписывает файлы на месте по всему модулю, включая `letter/*_test.go`. Если тестовые файлы не соответствуют форматтерам, go-code-developer изменит тестовую область — это запрещено процессом («Разделение обязанностей») и самим планом (таблица «Исполнители»: не меняет `letter/*_test.go`).
  2. `.golangci.yml` включает форматтер `gci` с разделами standard → `github.com/go-muse/musex` → прочие; golangci-lint v2 проверяет форматтеры и в `golangci-lint run` (CI, К-15). Тестовые файлы импортируют и `github.com/go-muse/musex/letter`, и `github.com/stretchr/testify/...`. Обычная группировка goimports сводит их в одну группу — `gofmt -l` это пропустит, `gci` — нет. План не требует от автора тестов проверки `gci`, хотя форматтерам компиляция не нужна, поэтому проверка выполнима и до реализации.
- **Почему проблема:** дефект тестовых файлов обнаружится только в plan-4 у автора, который не вправе их исправлять, либо будет «исправлен» им же через форматтер. В лучшем случае — лишний цикл через questions и review-tests, в худшем — нарушение разделения авторов.
- **Предложение:**
  - plan-4, п. 1: использовать проверку без записи — `golangci-lint fmt --diff ./...` (или ограничить запуск продуктовыми файлами: `golangci-lint fmt --diff letter/doc.go letter/letter.go …`) и прямо запретить запуск форматтера в режиме записи по тестовым файлам; замечания форматтера к тестам — вопрос автору тестов.
  - plan-1…plan-3, «Проверка шага»: добавить `golangci-lint fmt --diff` на своих файлах (пустой вывод) и ссылку на порядок импортов CONTRIBUTING.md (standard, `github.com/go-muse/musex`, сторонние — отдельными группами). Если команда до реализации окажется невыполнимой — записать фактическую диагностику и проверить порядок вручную.
  - «review-tests»: включить соответствие форматтерам `.golangci.yml` в проверяемое.
- **Адресат:** software-architect.

## Неблокирующие замечания

### Н-1. Вывод примеров не должен зависеть от текста ошибок вне контракта
- **Место:** architecture v2, `FromOrdinal` («точный текст не входит в контракт»), «Сводка» (`ErrInvalid = errors.New("letter: invalid letter")`), таблица «Исполняемые примеры Go» (`ExampleFromOrdinal`, необязательный `ExampleMustFromOrdinal`); implementation-plan v2, plan-2 («формат вывода выбирает автор тестов»).
- **Суть:** `// Output:` проверяется точным сравнением. Если пример напечатает `err` или восстановленную панику, ожидаемый текст выберет автор тестов, а реальный — автор реализации, не видящий тестов. Кроме того, неясно, входит ли в контракт текст самой `ErrInvalid` (в «Сводке» он показан, в разделе `ErrInvalid` — нет).
- **Предложение:** в plan-2 указать: в выводе примеров — только контрактные значения (`errors.Is(err, letter.ErrInvalid)` → `true`, `String`, числа), без `err.Error()`. В architecture явно сказать, входит ли `ErrInvalid.Error()` в контракт.
- **Адресат:** software-architect.

### Н-2. Числовые значения констант: «вне контракта» и «держать прежними» одновременно
- **Место:** architecture v2, «Тип `Letter`» («Числовые значения констант… не являются форматом хранения»), «Сериализация», Р-3.
- **Суть:** `encoding/json` (и json/v2, gob) кодируют `Letter` числом 1…7 без участия пакета. Пользователь, сохранивший структуру с буквой, зависит от этих чисел, не зная об этом. Р-3 ради Q-8 (а) обещает не менять числа, но публичный контракт говорит обратное.
- **Предложение:** привести к одному: либо в doc-комментарии `Letter` указать, что кодировщики на основе reflection выводят внутреннее число, оно стабильно, но не равно `Ordinal` и не рекомендуется для хранения; либо принять стабильность чисел как часть контракта. Решение остаётся за архитектором; новое поведение не требуется.
- **Адресат:** software-architect.

### Н-3. Изменение ROADMAP.md после приёмки не проходит ревью
- **Место:** implementation-plan v2, plan-6 («проверяет оркестратор»); architecture v2, «Компоненты», строка ROADMAP.
- **Суть:** по processes/rules/code-review.md изменения документации проекта проходят code-reviewer, кем бы они ни были сделаны; оркестратор не выносит профессиональный вердикт вместо ревьюера. plan-6 выполняется после приёмки и ревью в плане не имеет.
- **Предложение:** добавить после plan-6 короткое review-code по диффу ROADMAP.md (две правки) либо явно вынести решение о порядке на оркестратора и человека. Требование «ROADMAP.md не меняется до приёмки» (К-16) при этом сохраняется.
- **Адресат:** software-architect; порядок шагов — на решение оркестратора.

### Н-4. Проверки `FromOrdinal` и `MustFromOrdinal` слабее контракта
- **Место:** implementation-plan v2, plan-1 (Q-3: «`MustFromOrdinal(i)` для 0…6 без паники»); plan-3, К-7 («возвращённая буква недопустима»).
- **Суть:** для `MustFromOrdinal(i)` не проверяется, что результат — буква оракула с местом i; для ошибочного `FromOrdinal` контракт обещает именно нулевое `Letter`, а план проверяет только недопустимость (проходит и `Letter(42)`).
- **Предложение:** добавить `MustFromOrdinal(i) == оракул[i]` и `l == letter.Letter(0)` (или `var zero letter.Letter`) при ошибке `FromOrdinal`.
- **Адресат:** software-architect.

### Н-5. Создание ветки участником, у которого может не быть права
- **Место:** implementation-plan v2, «П-0. Ветка».
- **Суть:** docs/rules/main.md разрешает агентам создавать локальные ветки «в пределах полномочий их ролей». Есть ли у go-test-developer право «Git: запись», план не устанавливает; альтернатива «человек — по решению оркестратора» уже названа.
- **Предложение:** в поручении plan-1 оркестратору явно указать, кто создаёт ветку, с основанием права; иначе — человек до plan-1.
- **Адресат:** оркестратор (сведения); правка плана не обязательна.

### Н-6. `gofmt -l` в plan-4 перечисляет только два файла
- **Место:** implementation-plan v2, plan-4, «Проверка», п. 1.
- **Суть:** план разрешает дополнительные продуктовые файлы без `_test`, а проверка названа только для `doc.go` и `letter.go`.
- **Предложение:** «на всех изменённых продуктовых файлах пакета».
- **Адресат:** software-architect.

### Н-7. Большие значения `steps` проверяются только у краёв диапазона
- **Место:** implementation-plan v2, plan-1, К-5 (n ∈ [−15, 15]) и К-8 (`MaxInt − k`, `MinInt + k` для малых k).
- **Суть:** промежуточные большие значения (например, ±10^9, ±2^40, кратные 7 вблизи краёв) не перебираются. Реализация, корректная на краях и в малом диапазоне, но неверная посередине, маловероятна, однако оракул без переполнения позволяет дёшево проверить и это.
- **Предложение (по желанию):** добавить фиксированную выборку больших значений или `FuzzShift` с тем же оракулом (скилл golang-testing: числовые границы — свойства для fuzz). Если fuzz-цели добавляются, указать, что в CI они выполняются как обычные тесты по seed-корпусу.
- **Адресат:** software-architect.
