### Q-SA1. Правило «pointer receiver и возврат указателя» для буквы
- Адресат: человек (через оркестратора)
- Вопрос: правило docs/rules/dev.md «Для методов доменных объектов предпочтительно использовать pointer receiver, а так же возврат указателя на объект» для буквы без нарушения требований выполнить нельзя. Делаем ли для пакета `letter` исключение — методы и результаты по значению?
  - **(а) Исключение для `letter`: буква — значение.** `type Letter uint8`, константы `letter.C` … `letter.B`, методы с получателем по значению, результаты — значения.
    - Сравнение `==` работает по смыслу: `letter.C.Shift(9) == letter.E` — истина; буква годится ключом `map` и в `switch`.
    - Буквы — константы: изменить их нельзя никому; безопасно из любого числа горутин.
    - Цепочки, ради которых правило введено, работают: `letter.MustFromOrdinal(2).Shift(3).DistanceUp(letter.C)`; методы вызываются и на `*Letter`.
    - Must применяется как в dev.md: `MustFromOrdinal` — обёртка над `FromOrdinal` с паникой.
    - Отступление от «предпочтительного» правила фиксируется явно для `letter`. Тот же вопрос, вероятно, возникнет у других значений (alteration, spelling); их решают при их проектировании.
  - **(б) Применить правило буквально: `*Letter`.** Методы с получателем-указателем и возврат `*Letter`.
    - Констант букв не будет: буквы получают функциями (`letter.C()`).
    - Если функции отдают общие экземпляры, любой пользователь может перезаписать букву для всех (`*letter.C() = *letter.D()`) — нарушение требований о неизменяемости и параллельности (П-12, НФ-3).
    - Если каждый вызов создаёт новый объект, `==` сравнивает адреса: `C.Shift(9) == E` ложно — нарушение равенства букв (П-9, К-6); нужен метод `Equal`, буква не годится ключом `map`; выделение памяти на каждую операцию.
    - Появляется ещё одно недопустимое значение — `nil`, которое обрабатывает каждая операция.
    - Потребуется пересмотр требований (П-9, П-12, НФ-3) аналитиком и повторное ревью анализа.
- Зачем нужен ответ: правило и требования противоречат друг другу; docs/rules/main.md запрещает разрешать противоречие молча. От ответа зависит весь публичный контракт и все тесты; тесты не начинаются до ответа.
- Вариант по умолчанию: (а). Архитектура (step-7) и план (step-8) записаны для (а) в статусе «черновик»; при ответе (а) переходят в «готов» без изменений содержания.

  - на пример `*letter.C() = *letter.D()`: так делать не надо (недопустимый код, не аргумент);

### Q-SA1. Ответ архитектора на возражения (step-7/step-8, запуск 2, 2026-11-01)
- Адресат: человек (через оркестратора). Прежняя запись не меняется; здесь — разбор возражений и оба варианта заново.
- Сверка с requirements v3: «равенство» в П-9, С-6, О-6, К-6 — «одна ли это буква», а не оператор `==`. Метод `Equal` его выполняет. Прежнее утверждение «вариант (б) требует пересмотра требований» — неверно, снимаю.

#### По возражениям
1. **`==` и `Equal`.** Справедливо. Требования выполняются методом `Equal`. Остаётся практическое последствие, а не нарушение: `a == b` для указателей компилируется, и линтер его не ловит. Пока оба указателя выдал пакет, результат верный. Для копии, сделанной пользователем, он неверный (см. (б)). `Equal` нельзя использовать как ключ `map`, в `switch` и в `slices.Contains`; для них нужны `Ordinal()` или `*l`.
2. **`*letter.C() = *letter.D()`.** Справедливо: это злоупотребление, не аргумент. Так устроена стандартная библиотека: `time.UTC` — общий `*time.Location`, и его тоже технически можно перезаписать. Контракт (б) просто запрещает запись через указатель.
3. **Зачем константы.** Требования констант не требуют. Константы дают другое: компилятор гарантирует неизменяемость, повтор в `case` — ошибка компиляции, работают ключи `map` и `switch`, выделения памяти нет. Без констант буквы выдают функции `letter.C()`. Можно и экспортируемыми переменными `letter.C`, но тогда `letter.C = letter.D` меняет букву во всей программе.
4. **Конкурентность.** Справедливо. Общие объекты, которые никто не пишет, безопасны из любых горутин; НФ-3 выполняется и в (б).
5. **Какой тип у `Letter` в (а)** — ниже.

#### Вариант (а): `type Letter uint8`
- Это собственный именованный тип пакета. Внутри у него небольшое целое: 1 байт, значения 0…255. Так устроены `time.Month` (`type Month int`, `time.January`) и `time.Weekday`.
- Пользователь видит тип `letter.Letter`, семь констант и методы. С обычными числами тип не смешивается: `var n int = letter.C` — ошибка компиляции.
- Допустимы только семь констант; нулевое значение — «буква не задана».
```go
type Letter uint8
const (
    C Letter = 1 + iota // 1; numbers are not part of the contract
    D; E; F; G; A; B
)
func (l Letter) Shift(steps int) Letter
func (l Letter) DistanceUp(to Letter) int

l := letter.C                         // create
e := letter.MustFromOrdinal(2)        // E
letter.C.Shift(9) == letter.E         // true
letter.C.Shift(9).DistanceUp(letter.G) // 2: chain
m := map[letter.Letter]string{letter.A: "la"}
switch l { case letter.C: /* ... */ }
```
- Для единообразия с будущими типами можно добавить и `Equal(other Letter) bool`. Он дешёвый и ничего не ломает.

#### Вариант (б): по правилу dev.md
- Неизменяемый объект с неэкспортируемым полем, методы с получателем-указателем, возврат `*Letter`, `Equal`, Must.
- Буквы выдают функции `letter.C()`…`letter.B()`. Они возвращают указатели на семь общих объектов пакета, у которых нет методов изменения. Каждая операция (`Shift`, `FromOrdinal`, `All`) тоже отдаёт указатели на эти объекты. Поэтому операции не выделяют память; `All`/`Cycle` выделяют один срез из 7 указателей (56 байт).
```go
type Letter struct{ ord uint8 } // ord = place + 1; zero struct is invalid
func C() *Letter                // also D() … B()
func (l *Letter) Shift(steps int) *Letter
func (l *Letter) DistanceUp(to *Letter) int
func (l *Letter) Equal(other *Letter) bool
func FromOrdinal(ordinal int) (*Letter, error)
func MustFromOrdinal(ordinal int) *Letter

letter.C().Shift(9).Equal(letter.E())     // true
letter.MustFromOrdinal(2).Shift(3).DistanceUp(letter.C()) // chain
switch { case l.Equal(letter.C()): /* ... */ } // or: switch l.Ordinal()
m := map[int]string{letter.A().Ordinal(): "la"} // key: Ordinal or *l
```
- **Недопустимые значения:** `nil` и `&letter.Letter{}` (`new(letter.Letter)`). Каждый метод обрабатывает `nil`-получателя без паники: `IsValid` false, `Ordinal` и расстояния −1, `Shift` → nil, `Cycle` → nil. Поэтому цепочка на недопустимом значении не паникует.
- **`Equal`:** true только когда обе буквы допустимы и совпадают.
- **`==` вне контракта:** `letter.C().Shift(9) == letter.E()` случайно даёт true (один общий объект), но `p := new(letter.Letter); *p = *letter.E(); p == letter.E()` даёт false.
- **Требования:** П-9, С-6, О-6, К-6 выполняются через `Equal`. П-12, НФ-3, К-10, Г-3 выполняются при условии контракта «через указатель не писать»; по желанию аналитик может дописать это условие, переписывать требования не нужно. Е-1, К-7 выполняются: в таблицу недопустимых добавляются nil и пустая структура, тестов становится больше. Ревью анализа повторять не нужно; меняются architecture, план и будущие тесты.

#### Сравнение
| | (а) значение `uint8` | (б) `*Letter` по dev.md |
|---|---|---|
| Соответствие dev.md | исключение из «предпочтительно» | полное |
| Единообразие с будущими объектами-указателями | разный стиль (можно сгладить методом `Equal`) | одинаковый |
| Равенство | `==` и `Equal` (по желанию) | только `Equal`; `==` компилируется, но вне контракта |
| `map`, `switch`, `slices.Contains` | напрямую | через `Ordinal()`, `*l` или `Equal` |
| Недопустимые значения | одно: нулевое | `nil` и пустая структура; обработка nil в каждом методе |
| Выделения памяти | только срез в `All`/`Cycle` (7 байт) | только срез в `All`/`Cycle` (56 байт) |
| Защита от изменения | компилятор (константы) | контракт (запрет записи через указатель) |

### Q-H1. Как добавить набор из 12 букв и почему это не ломает текущий код (поручение q-human-12, запуск 1, 2026-11-02)
- Адресат: человек (через оркестратора). Вопрос человека 2026-11-02: «Как изменится код, когда мы добавим в неё 12-знаковую систему? … Как она будет жить параллельно с текущей? Что именно в текущей реализации подразумевает неломающее добавление такой системы?»
- Основания: architecture версии 5, раздел «НФ-1: будущие наборы букв» (а–д), КР-10, Р-4, Р-6; requirements версии 3, НФ-1 и К-11; Q-8 (а); domain-model версии 2, Д-3; текущий код `letter/letter.go`, `letter/doc.go` (только чтение).

#### 1. Как будет выглядеть код
- Существующий пакет `letter` не меняется. Для 12 букв добавляется **новый тип в отдельном подпакете**, например `letter/twelve` (имя условное): те же имена операций, тот же смысл по Д-3, другое число букв.
```go
package twelve // github.com/go-muse/musex/letter/twelve (name to be chosen)

type Letter uint8 // a letter of the twelve-letter set

const (
    L1 Letter = 1 + iota // placeholder names: real names come from research (I-3)
    L2
    // ...
    L12
)

const Count = 12
var ErrInvalid = errors.New("twelve: invalid letter")

func All() []Letter                            // 12 letters, canonical order
func FromOrdinal(ordinal int) (Letter, error)  // 0…11
func MustFromOrdinal(ordinal int) Letter
func (l Letter) IsValid() bool
func (l Letter) Equal(other Letter) bool
func (l Letter) Ordinal() int                  // 0…11
func (l Letter) DistanceUp(to Letter) int      // 0…11
func (l Letter) DistanceDown(to Letter) int    // 0…11
func (l Letter) Shift(steps int) Letter        // period 12
func (l Letter) Cycle() []Letter               // 12 elements
func (l Letter) String() string
```
- Общую арифметику круга (приведение по модулю, проверка места) можно вынести в приватный обобщённый пакет `letter/internal/...` и перевести на него оба набора. Это внутренняя перестройка без изменения поведения: architecture, НФ-1 в), «изменить»: только приватная реализация.
- Почему подпакет:
  - имена `C`…`B`, `Count`, `All`, `FromOrdinal`, `ErrInvalid` в `letter` уже заняты набором семи букв;
  - doc пакета говорит, что 7, 0…6 и период 7 — свойства набора семи букв, а иных наборов этот пакет не даёт;
  - решение 16 roadmap: варианты сущности — в подпакете.
- Альтернативы:
  - (а) Тот же пакет, тип `Letter12` и функции `All12`, `Count12`. Неломающе, но имена неудобны, и doc пакета пришлось бы дополнить.
  - (б) Обобщённый тип в `letter`: `type Of[S Set] uint8`, `letter.Of[Twelve]`. Удобно для многих наборов. Но текущий `Letter` придётся оставить отдельным типом: превращение его в псевдоним `Of[Seven]` меняет имя типа в reflection и `%T`, это тонкое ломающее изменение.
  - (в) Отдельный пакет верхнего уровня, например `letter12`. Равноценно подпакету, хуже группируется.

#### 2. Как два набора живут параллельно
- Это разные Go-типы. Смешать их нельзя — это ошибка компиляции, а не неверный результат (НФ-1 а: операции между наборами Д-3 не определяет).
```go
e := letter.C.Shift(9)        // E — exactly as today
x := twelve.L1.Shift(13)      // L2 — new code only
letter.C.Equal(twelve.L1)     // compile error: mismatched types
```
- Преобразований между наборами нет: что соответствует C в 12-буквенном наборе, домен не определяет (И-3, Д-3). Если понадобится — отдельная явная функция по доменному правилу, отдельным решением.
- Честно: Go разрешает числовое преобразование `letter.Letter(twelve.L3)` — у обоих типов в основе `uint8`. Результат бессмыслен. Защита — только документация («не поддерживается»), как и сейчас для `letter.Letter(n)`.
- Пользователь видит два импорта и два независимых словаря. Программа для семи букв ничего не замечает.
- Общий код для обоих наборов пишется через обобщённое ограничение. Текущий `letter.Letter` ему уже удовлетворяет — без единой правки:
```go
type Cyclic[L any] interface {
    comparable
    IsValid() bool
    Equal(L) bool
    Ordinal() int
    DistanceUp(L) int
    DistanceDown(L) int
    Shift(int) L
    Cycle() []L
    String() string
}

func Transpose[L Cyclic[L]](letters []L, steps int) []L

Transpose([]letter.Letter{letter.C, letter.E}, 2) // works with today's letter
Transpose([]twelve.Letter{twelve.L1}, 5)
```

#### 3. Что в текущем решении делает добавление неломающим (Q-8 (а))
- **Нет «текущего набора» как настройки.** Операции не принимают параметр набора, нет глобальной переменной или реестра (`SetDefault`). Новый набор не может изменить результат `letter.C.Shift(9)`.
- **Контракт привязан к набору семи букв.** Тип, `Count`, диапазоны и период описаны как свойства набора семи букв (НФ-1 п. 2, К-11 б). Новому набору не нужно переопределять старые обещания.
- **Методы возвращают и принимают свой тип:** `Shift` возвращает `Letter`, `DistanceUp` и `Equal` принимают `Letter`. Поэтому `Letter` подходит под обобщённое ограничение без изменений.
- **`Count` — константа, навсегда 7.** Код вида `[letter.Count]string` и `letter.Count*w + h` остаётся верным; у нового набора свой `Count`.
- **Стабильные числа C = 1 … B = 7, нет методов сериализации.** Хранимые данные и вывод `encoding/json` не меняются (Р-3).
- **Одинаковое поведение на недопустимых значениях:** −1, нулевое значение, nil, `"Letter(n)"`. Новый набор повторяет эту таблицу.
- **Пакет не импортирует ничего из musex.** Подпакет не создаёт циклов.
- Остаются неизменными: `Letter`, `C`…`B`, `Count`, `ErrInvalid`, `All`, `FromOrdinal`, `MustFromOrdinal` и все методы `Letter` — сигнатуры, результаты и документированный смысл (К-11 г).
- Добавить придётся: новый пакет и тип с операциями (НФ-1 в) п. 1–3), тесты и документацию к ним, по желанию обобщённое ограничение (п. 4) и приватное общее ядро. В doc `letter` — ссылку на другие наборы (дополнение текста).

#### Что может оказаться ломающим или неудобным
- **Главное — потребители.** `spelling`, `system`, `interval`, `notation` будут принимать и хранить `letter.Letter`, то есть будут написаны для семи букв. Чтобы они работали с 12 буквами, им нужны обобщённые или параллельные версии. Неломающе — только если добавлять новое, например `spelling.NameOf[L]`. Менять существующие сигнатуры, например поле `Name.Letter letter.Letter` на параметр типа, — ломающе. Цена расширения ляжет на всю ветку имён, а не на `letter`.
- **`Count` — константа пакета, а не метод.** Обобщённый код не может её получить. Нужен либо метод вроде `Len()`, который придётся добавить к `Letter` (совместимо, Р-4), либо `len(l.Cycle())` с выделением памяти. Формулы system (`u = 7w + h`) в обобщённом виде берут число букв из набора.
- **Две разные ошибки** `letter.ErrInvalid` и `twelve.ErrInvalid`. Обобщённому коду придётся проверять обе или ввести общую. Не ломает, но неудобно.
- **Добавление методов к `Letter`** ради общего интерфейса совместимо, но ломает код, который встраивает два типа с одноимённым методом (Р-4). Редко.
- **Круг.** Ограничение `Cyclic` предполагает, что набор замкнут в круг. Если 12-буквенная система окажется не круговой (Р-6, Н-7 ревью анализа), общий интерфейс к ней не подойдёт. Текущий код это не ломает: набор просто получит свой API.
- **Числовое преобразование между наборами** компилируется (раздел 2).
- **Псевдонимы.** Перевод `letter.Letter` на обобщённый тип через псевдоним меняет имя типа в reflection — его делать нельзя.

#### 4. Что остаётся открытым до реального расширения

#### Варианты
**A. Текущий.** `letter.Letter` — набор семи букв; будущий набор — в подпакете или отдельном пакете под своим доменным именем.

```go
// future: twelve.L1.Shift(13)
```

**B. Суффиксы в одном пакете: `letter.Letter7`, `letter.Letter12`.**
```go
letter.C7.Shift(9)   // constants need suffixes too: names C…B may repeat across sets

```
- Go не даёт пространств имён внутри пакета: суффикс получает **каждый** идентификатор — константы, `All`, `Count`, `FromOrdinal`, `ErrInvalid`. Это самый неудобный вариант.

**C. Предложение человека: `letter/seven` и `letter/twelve`.**

```go
package letter
```

- Общую `ErrInvalid` в `letter` класть не стоит: тогда `seven` импортировал бы родителя, а это ломает НФ-2. Направление импорта получилось бы обратным решению 15 roadmap: там родитель `octave` импортирует подпакеты.
